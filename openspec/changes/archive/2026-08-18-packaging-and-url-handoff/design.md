## Context

機能は揃ったが、配布形態が未確定でありセキュリティ上の必須要件も未充足である。

本アプリは Chromium を内蔵した「信頼できないコードを実行する装置」を自作したものである。CVE 追従を自動化しないまま常用するのは、既定ブラウザを使うより明確に危険である。自動更新は機能ではなく**前提条件**として扱う。

あわせて、Slack やドキュメントから開かれた AWS の URL が既定ブラウザに流れると、「AWS作業を専用ウィンドウに隔離する」という本アプリの目的そのものが崩れる。外部からの URL を本アプリへ引き込む経路を作る。

## Goals / Non-Goals

**Goals:**

- 署名済みアプリを配布可能にし、`safeStorage` の Keychain プロンプトを常用に耐える状態にする
- `electron-updater` により Chromium の CVE 追従を自動化する
- 外部から開かれた AWS の URL を、適切なアカウントのパーティションで開く
- Finicky との連携手順を文書化する

**Non-Goals:**

- Windows / Linux 向けの配布。macOS のみ
- Mac App Store 配布。サンドボックス要件と `screencapture` 呼び出しが噛み合わない
- 更新サーバの構築。既存のホスティング（GitHub Releases 等）を使う
- Finicky 自体の設定管理。ルール例の提供までとする

## Decisions

### D1: 自動更新は必須とし、無効化した構成を配布しない

「Chromium の CVE 追従を怠るなら、このアプリは作らないほうがよい」という判断を設計に固定する。`electron-updater` を有効にし、更新フィードは HTTPS、更新パッケージは署名検証を必須にする。

更新の取得に失敗した場合は現行バージョンで動作を継続する（起動不能にはしない）が、失敗は記録する。

### D2: 署名は Apple Developer 証明書を第一候補、ad-hoc をフォールバックとする

未署名だと `safeStorage` 参照のたびに Keychain プロンプトが出る。TOTP パネルを開くたび、SSO トークンを読むたびにプロンプトが出るのは常用に耐えない。

Apple Developer 証明書があれば署名＋公証を行う。なければ ad-hoc 署名で「初回許可すれば以降出ない」状態にする。ad-hoc の場合の制約（配布時に Gatekeeper の警告が出る等）を文書化する。

### D3: カスタムスキーム `aws-console://` と `open-url` の両方を受ける

- `aws-console://` — 本アプリ専用の明示的な経路。他アプリから確実に本アプリへ渡せる
- `open-url` — 既定ハンドラとして登録された場合に `https://` の AWS URL を受ける経路。Finicky からの委譲はこちら

両方を同じハンドラに集約し、URL 正規化後に共通の処理へ流す。

### D4: URL からアカウントを判定できない場合はパレットを出す

AWS コンソールの URL に `accountId` が含まれるとは限らない（`https://ap-northeast-1.console.aws.amazon.com/s3/buckets` にはアカウント情報がない）。

判定できない場合に「どこかのアカウントで勝手に開く」のは危険である。prod で開いてしまう可能性がある。**判定不能なら必ず利用者に選ばせる**。`sso-account-directory` のアカウント選択パレットを再利用する。

### D5: 受理した URL にも許可ドメインガードを適用する

外部から渡された URL をそのまま開くと、`navigation-guard` を迂回する経路になる。受理時点で `isAllowed()` を通し、許可外なら既定ブラウザへ返す。

### D6: 二重起動を避け、既存ウィンドウで開く

`open-url` を受けるたびに新しいウィンドウが増えると、「タブを溢れさせない」というアプリの目的に反する。シングルインスタンスロックを取り、既存ウィンドウのタブとして開く。

## Risks / Trade-offs

| リスク | 影響 | 緩和 |
|---|---|---|
| Apple Developer 証明書が用意できない | 配布時に Gatekeeper 警告、Keychain プロンプトの挙動が読めない | ad-hoc 署名にフォールバックし、制約を文書化する。個人利用では実害が小さい |
| 更新フィードが侵害される | 悪意ある更新の配信 | HTTPS + 署名検証を必須にする。署名検証に失敗した更新は適用しない |
| 更新でアプリが起動しなくなる | 常用不能 | 更新は次回起動時に適用し、失敗時は現行バージョンで継続する。ロールバック手順を文書化する |
| 外部URLの受理が `navigation-guard` を迂回する | 任意サイトがアプリ内で開く | D5 で受理時にガードを適用する |
| accountId 判定を誤って prod で開く | 誤操作事故 | D4 で判定不能時は必ず利用者に選ばせる。推測で開かない |
| Finicky ルールが広すぎて他の AWS 関連ページも吸い込む | 意図しない挙動 | ルール例を最小限（コンソール・ポータル・サインイン）に留め、`docs.aws.amazon.com` は含めない |
| 自動更新の頻度でコンソール作業が中断される | 摩擦 | 更新の適用は次回起動時とし、作業中に再起動を強制しない |

## Migration Plan

初回リリースであり移行対象はない。バージョニング方針と更新フィードの配信先を実装時に確定する。

ad-hoc 署名で開始し、Apple Developer 証明書が用意でき次第、署名済みビルドへ切り替える。切り替え時に `safeStorage` の鍵が変わり `sso.enc` / `totp.enc` が復号できなくなる可能性があるため、再インポート手順を用意する。

## Open Questions

- 更新フィードの配信先（GitHub Releases か自前ホスティングか）
- Apple Developer 証明書の有無
- **署名構成の変更で `safeStorage` の復号ができなくなるか** — 実測が必要。もし復号不能になるなら、ad-hoc 署名から正式署名への移行時にシードと SSO トークンの再登録が必要になる
- バージョニング方針（semver か日付ベースか）
