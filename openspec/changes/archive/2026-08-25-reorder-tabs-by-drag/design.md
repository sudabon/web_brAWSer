## Context

タブ順序の唯一の正は主プロセス `TabManager` の内部配列 `#tabs` である。`snapshots()` がサイドパネル表示用の配列を、`persisted()` が `tabs.json` 用の配列を、いずれもこの配列順のまま生成する。`Cmd+1`〜`Cmd+9` と `Cmd+Shift+[` / `]` も同じ配列順に依存する。したがって「並べ替え」とは `#tabs` の要素順を変えることに等しく、表示・永続化・ショートカットは追加の同期処理なしで追従する。

現在レンダラーへ公開されているタブ操作は `list / open / select / close / rename` のみで、順序を変更する経路が存在しない。レンダラーは `tabs:changed` を購読して `TabSnapshot[]` をそのまま `useState` に保持する片方向フローになっている。

D&D の既存実装はファイルドロップを受ける `TotpPanel.tsx` のみで、並べ替え用のライブラリは導入されていない。

## Goals / Non-Goals

**Goals:**

- サイドパネルのタブ行をドラッグ＆ドロップで任意の位置へ移動できる
- 並べ替え結果が `tabs.json` に永続化され、再起動後も維持される
- 既存の片方向データフロー（主プロセスが正 → `tabs:changed` で通知）を崩さない
- 依存パッケージを増やさない

**Non-Goals:**

- キーボードによる並べ替え
- タブのグループ化・ピン留め・アカウント別のセクション分割
- 長大なタブリストでのドラッグ中の自動スクロール（必要になった時点で別変更）
- ドラッグによるアカウント×ロールの付け替え（並べ替えは表示位置のみを変える）

## Decisions

### 1. HTML5 ネイティブ D&D を使う

`<li>` に `draggable` を付け、`dragstart` / `dragover` / `dragleave` / `drop` / `dragend` で処理する。

- **理由**: 対象は縦一列の単純なリストで、必要なのは「掴む・挿入位置を示す・落とす」だけ。実行環境が Electron（Chromium 単一）のためブラウザ差異を考慮する必要がない。バンドルサイズと依存の増加を避けられる
- **代替案 `dnd-kit` / `react-dnd`**: アクセシビリティ対応や自動スクロールが標準で付くが、この規模の要件に対して依存追加のコストが見合わない
- **代替案 Pointer Events を自前実装**: 既存の `onResizePointerDown`（パネル幅リサイズ）と手触りを揃えられるが、ドラッグ中のゴースト表示・挿入位置計算・キャンセル処理をすべて自作することになりコード量が増える

### 2. IPC はインデックス指定（`tabs:reorder(id, toIndex)`）

順序配列全体を送る `setOrder(ids[])` ではなく、「どのタブをどの位置へ」の差分を送る。

- **理由**: レンダラーが持つスナップショットとメイン側の配列は非同期にずれうる。全順序を送る方式では、ドラッグ中に別経路でタブが開かれた場合にそのタブが順序配列から抜け落ちる危険がある。ID 指定なら未知の ID は no-op、`toIndex` は現在の長さでクランプすれば安全側に倒れる
- **`TabManager.reorderTab(id, toIndex)`** は配列から対象を取り出して挿入し直し、`#persist()` と `options.onChange()` を呼ぶ。既存の `renameTab` と同じ形

### 3. 楽観的更新を行わない

ドロップ時は IPC を投げるだけで、表示順の更新は `tabs:changed` の受信に任せる。

- **理由**: `reorderTab` は同期処理のうえ `onChange()` を即座に呼ぶため往復は実質的に無視できる。`rename` / `close` も同じ経路で体感上の問題が出ていない。レンダラー側にローカル順序を持つと主プロセスとの二重管理になり、`tabs:changed` との整合を取るコードが増える

### 4. ドロップ位置は行の中央線で判定する

`dragover` で対象行の矩形を取り、ポインタが中央より上なら「その行の前」、下なら「その行の後」に挿入する。挿入位置は `.drop-before` / `.drop-after` のクラスで線として表示する。

- **理由**: 行と行の隙間を狙わせるより命中精度が高く、リストの末尾へ落とす操作も最終行の下半分で自然に表現できる

### 5. 選択・リネームとの競合はレンダラー側で抑止する

- タブ名編集中（`<input>` 表示中）は `draggable={false}` にする。テキスト選択のドラッグを D&D に奪わせないため
- `dragstart` からフラグを立て、`dragend` で下ろす。ドラッグ由来の `click` はこのフラグで無視し、タブ選択を発火させない
- ダブルクリックによるリネーム開始は従来どおり動く（`dblclick` は `dragstart` と競合しない）

### 6. 並べ替えはタブの状態を変えない

アクティブタブ、ハイバネート状態、`WebContentsView` の bounds、所属パーティションはいずれも変更しない。順序変更は `#tabs` の要素順のみに作用する。

## Risks / Trade-offs

- **ドラッグ操作が意図せずタブ選択を発火させる** → `dragstart` / `dragend` のフラグで `click` を抑止し、テストで「並べ替え後にアクティブタブが変わらない」ことを確認する
- **`Cmd+1`〜`Cmd+9` の割り当てが並べ替えで変わる** → 仕様上の意図した挙動。番号は表示順に追従するという既存要件のままであり、提案書の Impact に明記する
- **レンダラーのスナップショットが古い状態で `toIndex` を送る** → `reorderTab` 側で ID 存在確認と範囲クランプを行い、不正な入力は no-op または端への移動に丸める
- **タブ数が多いときドラッグ中にリストが自動スクロールしない** → 今回のスコープ外。運用上支障が出た場合に別変更で対応する
- **マウス操作専用になりキーボードだけでは並べ替えできない** → Non-goal として明示。`Alt+↑/↓` などの追加は別変更で起票する

## Migration Plan

`tabs.json` のスキーマは変更しない（配列順の意味が「開いた順」から「利用者が決めた順」に変わるだけ）。既存の保存ファイルはそのまま読み込め、初回は従来どおりの順序で表示される。ロールバックは実装のリバートのみで完了し、データ移行は不要。

## Open Questions

- キーボードによる並べ替え（`Alt+↑/↓` 等）を後続で入れるか。今回は Non-goal とし、実利用で必要性が確認できた時点で判断する
